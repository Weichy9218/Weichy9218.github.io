MCP（Model Context Protocol）架构与工程笔记

Chuyang Wei · Agent Infrastructure / Protocol

MCP（Model Context Protocol）是由 Anthropic 发起并开源的一套上下文与工具接入协议。如果说 LSP（Language Server Protocol）把“不同编辑器 × 不同编程语言”的集成复杂度从 M × N 降成了 M + N，MCP 做的就是同一件事：把不同 AI 应用（Host）与不同外部数据源、工具、服务（Server）之间的通信接口标准化，避免每个 Agent 框架都要为数据库、GitHub、Slack、本地文件系统重写一遍适配胶水代码。

一、先把概念边界划清：Function Calling、MCP 与 Agent

这几个词经常被混在一起说，其实它们分别落在不同层级，彼此是配合关系而非替代关系：

概念 所在层级 核心职责 典型形态
Function Calling 模型能力层 模型根据上下文判断何时调用外部能力，并输出结构化参数（如 JSON） OpenAI / Claude / Gemini API 的 tools 参数
MCP 通信协议层 规定 AI 应用如何发现、鉴权、调用外部工具与读取上下文资源，与具体模型解耦 基于 JSON-RPC 2.0 的 Client–Server 协议
AI Agent 系统循环层 编排规划、记忆、工具调用与环境反馈循环，自主推进多步任务 借助 Function Calling 决定动作，通过 MCP 执行外部交互

一句话概括：Function Calling 解决“模型怎么提出调用请求”，MCP 解决“宿主应用怎么用统一协议去连各种外部工具”，Agent 负责把多步调用串成闭环。

二、整体架构与传输层

MCP 采用经典的 Host – Client – Server 三层角色划分，底层的消息编码统一使用 JSON-RPC 2.0：

  • Host（宿主）：直接面对用户的 AI 应用（如 IDE、桌面客户端或自研 Agent Runtime），负责拉起和管理多个 Client，汇总上下文，并把控敏感操作的权限审批。
  • Client（客户端）：嵌在 Host 内部，与某个特定 Server 保持 1:1 连接，负责握手协商、能力发现与消息路由。这样可以把不同 Server 的故障与权限相互隔离。
  • Server（服务端）：轻量级能力提供方，通过标准接口向外暴露 Tools、Resources 和 Prompts，背后可以接本地进程，也可以代理远程云服务。

传输层（Transport）目前主要有两种：本地工具常用 stdio（Host 直接把 Server 当子进程拉起，零网络配置、延迟低）；远程服务则走 Streamable HTTP（取代了早期独立的 HTTP+SSE 拆分方案，更适配无状态部署与标准鉴权中间件）。

三、三大核心原语与控制权划分

MCP 把 Server 能提供的东西抽象成三类原语，有意思的是它们对应着三种不同的调用控制权：

原语 控制方 定位与例子
Tools 模型控制（Model-controlled） 可执行、可能产生副作用的操作，如查数据库、发请求、改代码、跑测试；需经 Host 安全策略或用户确认
Resources 应用控制（Application-controlled） 以 URI 标识的只读上下文数据，如文件内容、日志快照、表结构 Schema，由 Host 决定何时塞进上下文
Prompts 用户控制（User-controlled） Server 预置的可复用提示词模板或工作流入口（例如在聊天框里用 / 显式触发）

此外，协议还留了反向通道（如 sampling），允许 Server 在必要时向 Host 请求做一次 LLM 补全，但最终是否放行、用什么模型、给多少预算依然由 Host 掌握。

四、基本交互生命周期

一次完整的 MCP 会话通常分四步：能力握手 → 发现能力 → 执行调用 → 关闭连接。

  1. 初始化握手（initialize）：Client 与 Server 交换协议版本和双方支持的能力集（capabilities），随后发送 notifications/initialized 确认就绪。
  2. 能力发现（tools/list / resources/list）：Client 拉取可用工具的名称、自然语言描述和 JSON Schema 参数定义，交给 Host 拼入模型上下文。
  3. 执行调用（tools/call）：模型产出调用意图后，Client 把请求发往对应 Server，Server 执行具体逻辑并返回结构化内容或错误信息。
  4. 会话结束：任务完成或 Host 退出时关闭传输通道（stdio 关闭子进程，HTTP 终止会话）。 
// Client -> Server: 调用工具
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "query_papers",
    "arguments": { "topic": "delayed feedback", "limit": 5 }
  }
}

// Server -> Client: 返回结果
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [{ "type": "text", "text": "..." }],
    "isError": false
  }
}

五、工程落地里的几个真实取舍

把 MCP 真正接入 Agent 系统之后，有几个痛点很值得提前想清楚：

  • 工具 Schema 膨胀吃上下文：一旦同时挂载十几个 MCP Server、上百个工具，光把所有 tools/list 的 JSON Schema 全塞进 system prompt 就可能吃掉数万 token，还会明显拉低模型选工具的准确率。实际工程里往往需要配合按需检索（tool search）或渐进式加载，而不是无脑全量暴露。
  • 安全边界与 Prompt Injection：外部工具返回的数据本身不可信，一旦工具同时具备“读外部网页/邮件”和“写本地文件/发网络请求”两类权限，就存在间接提示词注入风险。权限审批与沙盒隔离必须由 Host 兜底，不能指望模型自觉遵守。
  • 什么时候不必硬上 MCP：MCP 最大的红利在于跨应用复用和生态共享（一次写好 Server，多个客户端直接用）。如果只是自家单一 Agent 内部的轻量脚本或高吞吐推理管线，直接调本地 CLI 或原生函数往往比多绕一层进程/RPC 更轻、更好调试。
