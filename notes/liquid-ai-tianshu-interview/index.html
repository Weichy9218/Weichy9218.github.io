INTERVIEW NOTE | 2026-11-26

验证速度决定迭代上限

Liquid AI 于天舒访谈笔记 | RSI / Agentic RL / Data Scaling

最近看了月球大叔在 SGLang Summit 现场采访 Liquid AI 工程师 于天舒（Tianshu Yu）的视频（《让大模型在边缘设备跑？》↗）。他之前在字节带过 RL Infra，也是 veRL 的核心贡献者，加入 Liquid AI 一年来从推理优化一路做到 RL Infra，又做到视觉语言模型（VLM）的预训练和架构设计，最近刚参与发布第三代模型 LFM3（视觉能力明显提升，并新增了视频理解）。

整段采访 13 分钟，聊得非常直接。开头他先点出了 Liquid AI 和 OpenAI、Anthropic、Thinking Machines 的定位差异：他们死磕的是效率与硬件定制。比如和奔驰合作车载智能时，车机只能分出极小一块硬件资源，团队必须在硬约束下专门设计 1B 参数以下的模型，把车载语音助手等功能跑顺。

往下聊到训练、RL、评测和 RSI 时，他讲的几个技术判断很实在，下面结合原话和少量直接相关的文献记下来。

1. 模型出问题，最后大多还是 Data Scaling 和数据体感问题

被问到 Pre-training、Test-time、RL 几种 Scaling 哪个最重要，于天舒没有犹豫，直接选了 Data Scaling：

“很多很多的问题都是因为 data 要么是 diversity 不够，要么是 task 合成的东西不够……需要一个非常好的 data pipeline，能从各种 source 里面 scrape data，systematically clean，有 quality control，有看板能看每个训练 batch 里面有多少 data 属于哪种类型、哪种知识。Data 是最最最 valuable 的部分。”

关于数据，访谈里有两个很具体的一线体感：

  • 数据目前依然是重人力活，Agent 替不了人的「data sense」。他的原话很直白：“你即使有智能体，智能体它其实没有太好的 data sense。很多时候就得用 human eye 去 vibe check 这个 data 到底可能会有什么问题，然后看损失曲线，曲线不太对，得判断到底是 data 有问题，还是 infra 里面有点 bug。”（他在 Redpanda Hello, Agent! 播客里也提过，训练里最难排查的往往不是直接报错崩溃，而是浮点舍入漂移、微调数据分布过于集中导致的能力坍缩这类静默问题。）
  • 为什么暂时不采购 Mercor / Scale AI / Surge AI 的数据。一是价格贵；二是他们发现自己内部合成的数据，叠加真实企业客户场景数据，已经基本覆盖了外包商能提供的大部分内容，目前还没到必须花大钱外采稀缺数据的阶段。

学术界近期的对照实验也印证了这两点：一方面，预训练数据配比正从拍脑袋转向小代理模型量化预测（如 RegMix，ICLR 2025）；另一方面，专门评测“Agent 做数据研究员”的 RSIBench-Data（arXiv:2607.25886）发现，让 LLM Agent 自主诊断短板、调数据配方、微调再迭代，一半以上情况首轮能涨点，但拉长轮次后很容易越调越偏、最终掉到峰值以下。跑清洗脚本可以交给 Agent，但盯着样本和 loss 曲线揪出异常，现阶段还是人的手艺。

2. 多轮 Agent RL 与 Benchmark：真正卡住迭代的是工程周转

聊到最近很火的造环境（RL environment），于天舒直接指出了单轮和多轮的工程分水岭：

“在 RL infra 里，environment 真的是非常复杂的一个部分。一开始如果是 single-turn agent 还好，如果你是 multi-turn agent 的话，你会需要有沙盒（sandbox）。如何在有沙盒的环境下，让整个训练任务 GPU 不闲置，这都是很有挑战的。”

单轮数学或代码任务里，rollout 基本是纯 GPU 推理；一旦进入多轮 Agent 交互，每条轨迹都要反复经历「模型生成 → CPU 沙盒执行命令/测试 → 等待结果回传」。如果沿用同步批处理，昂贵的 GPU 集群只能干等批次里最慢的那个长尾沙盒（straggler），利用率会迅速骤降。这两年从 veRL（HybridFlow）扩展出的异步 server rollout，到 AReaL（arXiv:2505.24298）彻底解耦 rollout 与训练、用 staleness-aware PPO 控住策略陈旧度（相比同步最高提速 2.77×），再到 SkyRL 专门针对多轮工具调用做流水线调度，核心都是在解同一件事：在不把训练搞崩的前提下，把 GPU 空转的气泡压掉。

另一个被他单独拎出来的工程卡点是 Benchmark：

“Benchmark 最大的就是要跑得快，因为现在 benchmark 越来越多……而且 comparison 要 fair。很多时候 prompt 换一下，或者 reasoning 强度换一下，模型的 score 都没有可比性。所以需要一个好的 benchmark 看板，有 systematic 的方式让你边训模型就可以边 eval，这样才能有很好的迭代 feedback。”

Sclar 等人（ICLR 2024，arXiv:2310.11324）测过，仅改变语义等价的 prompt 格式，模型分数就能波动几十个点；到了推理模型阶段，不同思考预算下的分数更没法直接拉齐。所以评测基建的价值不只是出榜，而是要做成能“边训边评、口径严格对齐”的高频反馈表。

3. 可验证只是前提，验证速度才决定 RSI 能不能转起来

关于硅谷热炒的 RSI（递归自我改进），于天舒先讲了现实，再讲了目标：

“如果说是用 Claude 或者是 Codex 来做我们 infrastructure 的 implementation，那么确实某种意义上来说是 RSI；但我们并没有训练 OpenAI 的模型，所以也不能说是完全的 RSI……我们之后也要训练 DeepSeek-level 的模型，但是能 running on device。等越来越接近 frontier 模型之后，我也会想做一些 in-house 比如 coding 的模型，至少先把我们自己的 infra optimize 快一点。”

Liquid AI 官方在 2026 年 8 月发过一篇很实在的工程记录（Designing Loops for Production-Grade Work），正好印证了这种“准 RSI”的真实工作方式：他们让 Claude Opus 4.5 和 Codex 从零写一个单机跑万亿 token 的 Rust BPE 分词器训练引擎（toktoktok）。两个模型都在 30 分钟内写出了能过单元测试的玩具版，但一接真实生产语料全部失败：跑到 1% 语料就 OOM、Parquet 多编码静默出错、正则回溯退化成平方复杂度。最后 Claude Opus 4.5 能收出生产代码，靠的不是哪次 zero-shot 写得多神，而是外面那套 Agent 篡改不了的真实语料与第三方校验循环，撞墙、看 profile、改完再跑，一轮轮磨出来的。

而整场访谈里最有意思的技术判断，出现在被问到“AI 多久会取代 AI 从业者、最大的壁垒是什么”时。他估了个 4–5 年的窗口，但对行业里很流行的说法（“只要任务是 verifiable 的，就很容易被 AI 取代”）直接提出了怀疑：

“因为你 verify 的这个速度，会很大程度限制你这个模型迭代的速度。假如我们要取代 AI researcher，训一次模型可能一个月才能看到 feedback，那你能 RL 多少次呢？以我们现在这种 RL 算法的效率，都不知道要等到猴年马月才能有个很好的 AI research 的 sense。”

Jason Wei 在 Asymmetry of Verification（Verifier's Law）里讲的是“能不能验证”，于天舒补上了一个落到训练里绕不开的物理限制：可验证只是前提，验证要等多久，才决定了 RL 迭代循环转不转得起来。

近两年的几个代表性工作，几乎把这条边界画得很清楚：

  • DeepMind 的 AlphaEvolve（arXiv:2506.13131）在矩阵乘法、集群调度和底层 kernel 上效果突出，因为程序验证几秒到几分钟就能出结果；
  • Karpathy 的 autoresearch 更干脆，直接把每次训练实验硬压到 5 分钟，人为把验证延迟压到极低，换取一夜跑上百轮的试错密度；
  • 反过来，METR 的 RE-Bench（arXiv:2411.15114）拿 AI Agent 和人类 ML 专家做过对照：在 2 小时短预算下，前沿 Agent 得分约是人类专家的 4 倍；可预算拉长到 8 小时以上，人类专家就反超了。

换句话说，只要当前 RL 算法的样本效率还没发生质变，那些单次验证耗时数周甚至数月的长反馈任务，很难单靠暴力试错跑通自我迭代。

Tip：展开看与我自己研究方向的几点呼应

于天舒讲多轮环境、评测和验证速度这几段，跟我在预测 Agent 和自演化方向上碰到的其实是同一类问题：

  • 验证延迟（Delayed Feedback）：开放世界预测和大模型训练一样，结果最终可验证，但动辄要等几周、几个月。与其干等最终结果，不如挖掘等待期间不断冒出来的中间证据（pre-resolution signals）来做信用分配与在线修正（Milkyway）；同时在真实异步环境里维护轨迹与评测口径（FutureWorld、DEEPRUBRIC）。
  • 提高单次试错的信息利用率：既然长周期任务试错不起，就需要先把经验持久化沉淀到可演化的 Agent harness（记忆、技能、工作流，见我们维护的 Harness-RSI），再逐步通过 on-policy 训练内化进模型权重，而不是每次都从头盲搜。

附：访谈里聊到的工程直觉与商业判断

除核心技术之外，访谈后半段还聊了不少创业、商业和招人方面的实在话，简记几条：

  • 用 AI 写代码时代的工程直觉（Roofline 算账）：团队目前依然很缺推理和 RL Infra 工程师，招人最看重第一性原理。他举了个具体例子：优化推理 MFU 时，不能只跑一下 Claude 改改代码、汇报 token/s 比原来快了多少就交差，得先算清硬件峰值多少 TFLOPS/s、单次 forward 理论多少 TFLOPS、打满物理极限应跑多少 request/s，再看现状和物理上限差了多少（也就是经典的 Roofline 思维）。
  • 大厂 vs 创业公司：“在大厂里得 convince 七八个 VP 才能做某个项目；在创业公司就是 I just do it。”被问到公司文化对个人的支撑时，他反倒觉得，有热情、讲第一性原理的人是可以反过来改变公司文化的。
  • 资本效率与壁垒演化：相比靠重债务建数据中心的高融资 Neo Lab，Liquid AI 刻意不背债、压低算力相对人力的开支比例，按可持续商业逻辑经营。面对巨头小模型（OpenAI mini、Claude Haiku），他总结了一套三步走：短期靠更聪明的技术破局，趁技术还没被追平赶紧转化为车企长约这类分发锁定，再把赚到的资本沉淀成中长期基建壁垒。
  • 关于四五年后的个人出路：被问到 AI 从业者以后做什么，他认真说了水电工创业；被追问机器人可能也会干水电工后，改口说想做一家带点科技感的物理安保公司（“真不是搞抽象，我真是这么想的”）。
