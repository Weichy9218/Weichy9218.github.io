听完 Liquid AI 于天舒访谈的一些笔记：数据、多轮 RL、验证速度与工程直觉

Chuyang Wei · 标签：RSI / Delayed Feedback / Agentic RL / Liquid AI

最近刷到月球大叔在 SGLang Summit 现场采访 Liquid AI 工程师 于天舒（Tianshu Yu）的视频（《让大模型在边缘设备跑？》↗）。他之前在字节带过 RL Infra，也是 veRL 的核心贡献者，去 Liquid AI 一年左右，从推理优化一路做到 RL Infra，又做到视觉语言模型（VLM）的预训练和架构。

整段采访只有 13 分钟，聊得很实在，基本没什么公关词。里面有几个点——数据体感、多轮 RL 的工程卡点、验证速度，还有工程里的第一性原理——跟我自己平时关心的延迟反馈、Agent harness 演化和 RSI 挺有共鸣。把他的核心原话和少数几个直接相关的研究整理一下，留个笔记。

一、Data Scaling：模型的问题，最后大多还是数据问题

被问到 Pre-training、Test-time、RL 几种 Scaling 哪个最重要时，于天舒直接选了 Data Scaling。他的判断很朴素：模型很多毛病，追到底要么是数据多样性不够，要么是任务合成不到位。真正值钱的是一套系统化的数据基建——从各种来源抓取、清洗、做质控，再配一个看板，能看清每个训练 batch 里各类知识和数据的占比。

访谈里关于数据的两个细节听完很有感触：

  • 数据目前还是重人力活，Agent 替不了人的「data sense」。他的原话很直接：“你即使有智能体，智能体它其实没有太好的 data sense。很多时候就得用 human eye 去 vibe check 这个 data 到底可能有什么问题，然后看损失曲线——曲线不太对，得判断到底是 data 有问题，还是 infra 里面有 bug。”（他在 Redpanda Hello, Agent! 播客里也提过类似的一线坑：训练里最难搞的往往不是直接报错崩溃，而是浮点漂移、微调数据过度集中导致的能力坍缩这类静默问题。）
  • 为什么暂时不买 Mercor / Scale AI / Surge AI 的数据。原因也挺现实：一是贵；二是他们发现自己内部合成的数据，加上真实企业客户的数据，已经覆盖了外包商能提供的大部分内容，目前还没到非花大钱外采不可的阶段。

学术界最近也有挺直接的呼应。预训练数据配比已经开始从拍脑袋转向小代理模型量化预测（比如 RegMix，ICLR 2025）；而关于“Agent 缺 data sense”，今年有一篇 RSIBench-Data（arXiv:2607.25886）专门测了 LLM Agent 当“数据研究员”的效果——让它自己诊断模型短板、改数据配比、微调再迭代。结果一半以上情况第一轮能涨点，但拉长迭代轮次后很容易越调越偏，最后反而掉到峰值下面。Agent 很会跑清洗脚本，但看一眼样本和 loss 曲线就嗅出哪里不对劲，现阶段还是得靠人。

二、多轮 Agent RL 与 Benchmark：卡住人的往往是工程周转

谈到大家都在卷的 RL environment（造环境），于天舒点出了单轮和多轮的分水岭：

“如果是 single-turn agent 还好，如果你是 multi-turn agent 的话，你会需要有沙盒（sandbox）。如何在有沙盒的环境下，让整个训练任务 GPU 不闲置，这都是很有挑战的。”

这确实是这两年 Agent RL 基础设施最核心的矛盾。单轮数学或代码任务里，rollout 基本是纯 GPU 推理；一进入多轮交互，每条轨迹要不停地「生成 → 进 CPU 沙盒跑命令/测试 → 等结果回来再继续」，一旦走传统的同步批处理，昂贵的 GPU 集群就得干等批次里最慢的那个长尾任务，利用率会掉得很厉害。所以从 veRL（HybridFlow）后来扩展出的异步 rollout，到 AReaL（arXiv:2505.24298）把 rollout 和训练彻底解耦、靠 staleness-aware PPO 控住异步带来的策略陈旧度，再到 SkyRL 针对多轮工具调用做流水线调度，本质都是在解同一个问题：怎么在不把训练搞崩的前提下，把 GPU 空转的气泡压掉。

另一个他反复强调的痛点是 Benchmark：

“Benchmark 最大的就是要跑得快，因为现在 benchmark 越来越多……而且 comparison 要 fair。很多时候 prompt 换一下，或者 reasoning 强度换一下，模型的 score 都没有可比性。所以需要一个好的 benchmark 看板，让你边训模型就可以边 eval，这样才能有很好的迭代 feedback。”

Sclar 等人（ICLR 2024，arXiv:2310.11324）早就测过，哪怕只改语义等价的 prompt 排版，模型准确率都能上下晃几十个点；到了推理模型时代，不同思考预算下的分数更不好硬比。这也让我想到我们自己在做 FutureWorld 和 DEEPRUBRIC 时的切身体会——只要任务从封闭题库走向真实环境或复杂 rubric，评测的稳定性、吞吐和信噪比，往往比换一个 RL 算法本身更早卡住迭代。

三、RSI 的现状，以及比「可验证」更现实的「验证速度」

聊到很火的 RSI（递归自我改进），于天舒的态度挺克制：平时用 Claude 或 Codex 来写自己的 infra 代码，某种意义上算沾边 RSI，但毕竟不是自家模型反哺自家。他们接下来的打算，是训出能跑在端侧的 DeepSeek 级别模型，等模型能力靠近前沿之后，再做内部 coding 模型，至少先用来优化自家 infra。

顺着这个点，我又翻了 Liquid AI 自己写的一篇工程记录（Designing Loops for Production-Grade Work）：他们让 Claude Opus 4.5 和 Codex 从零写一个单机跑万亿 token 的 Rust BPE 分词器训练引擎（toktoktok）。结果两个模型都在 30 分钟内写出了能过单元测试的玩具版，但一上真实语料全挂——跑到 1% 语料就 OOM、Parquet 编码静默出错、正则回溯退化成平方复杂度。最后 Claude Opus 4.5 能交付生产代码，靠的不是哪一次 zero-shot 写得多神，而是外面那套 Agent 篡改不了的真实数据和第三方校验循环，撞墙、看 profile、改完再跑，一轮轮收出来的。

这也顺理成章地引出了整段访谈里我最有共鸣的部分。主持人问“AI 多久会取代 AI 从业者、最大的壁垒是什么”，于天舒估了四五年，但对圈里很流行的那句话——“只要任务是 verifiable（可验证）的，AI 很快就能取代人”——直接表示怀疑：

“因为你 verify 的这个速度，会很大程度限制你这个模型迭代的速度。假如我们要取代 AI researcher，训一次模型可能一个月才能看到 feedback，那你能 RL 多少次呢？以我们现在这种 RL 算法的效率，都不知道要等到猴年马月才能有个很好的 AI research 的 sense。”

Jason Wei 的 Asymmetry of Verification（Verifier's Law）把“能不能验证”讲得很透，但于天舒补上了一个落到工程里绕不开的现实条件：可验证只是前提，验证要等多久，才决定了 RL 的闭环转不转得起来。

这两年的几个代表性工作，几乎把这条边界画得很明白：

  • DeepMind 的 AlphaEvolve（arXiv:2506.13131）在矩阵乘法、集群调度和底层 kernel 上效果很惊人，因为这些任务的程序验证几秒到几分钟就能出结果；
  • Karpathy 的 autoresearch 更干脆，直接把每次训练实验硬压到 5 分钟，用极短的验证周期换一夜跑上百轮的试错密度；
  • 反过来，METR 的 RE-Bench（arXiv:2411.15114）拿 AI Agent 和人类 ML 专家做过对照：在 2 小时短预算下，前沿 Agent 得分能到人类专家的 4 倍左右；但一旦预算放到 8 小时以上，人类专家就反超了。

这里其实直接回到了我自己最关心的研究问题上。现实世界里大量重要任务——不管是训一个大模型，还是开放世界里的未来事件预测——结果最终都是客观可验证的，但反馈延迟动辄几周甚至几个月（delayed feedback）。靠现在动辄几万次 rollout 的 RL 样本效率，根本等不起。

要绕过或者压缩这层延迟，我觉得大体只有两个方向值得深挖：

  1. 别干等最终结果揭晓。在漫长的等待过程里，环境其实一直在放出中间证据（pre-resolution signals），怎么用这些时序上的中间信号来做信用分配、校准和纠错，是我们在 Milkyway 里一直在试的路子；
  2. 把单次昂贵试错榨出更多信息。既然不能靠暴力试错撞大运，就得把每次实验或任务里的经验先沉淀到可持久化的 Agent harness（记忆、技能、工作流，见我维护的 Awesome Harness Self-Evolving），再通过 on-policy 训练慢慢内化进模型权重，而不是每次换个任务又从零摸索。

四、创业公司节奏，以及 AI 写代码时代的「第一性原理」

聊到大厂和创业公司的区别，于天舒说得特别干脆：“在大厂里得 convince 七八个 VP 才能做某个项目；在创业公司就是 I just do it。”主持人顺势说这是好公司文化赋能了个人，他倒没顺着接，反而觉得：只要你是个用第一性原理想问题、又有热情的人，你是能反过来改变公司文化的。

关于招人，他提到团队目前依然很缺推理和 RL Infra 工程师，没有因为 AI 工具就把岗位砍掉，招人最看重的就是 First Principles Thinker。他举的那个例子非常具体，拿来当面试题都很合适：

“比如我们要把模型的 inference MFU 提上去，他不能跟我说：‘我就 run 了一个 Claude，现在看多少 token/s，比原来快了多少’，就说任务完成了。不！我需要看到的是：首先，你现在跑的硬件是多少 TFLOPS/s；你的模型理论上一次 forward pass 是多少 TFLOPS；如果用满硬件的物理极限，应该处理多少 request/s；再看你现在和理论物理极限差了多少。”

这其实就是系统优化里经典的 Roofline 思维（像 Horace He 的 Making Deep Learning Go Brrrr From First Principles，以及 Google 的 How to Scale Your Model 讲的都是同一套算账方法）。

用上 Claude Code 或 Codex 之后，这件事反而更有意思了。Coding Agent 特别擅长做局部优化——把一段慢代码改一改、提速 20% 很容易；但如果当前实现只跑到了芯片物理上限的 15%，提速 20% 之后也才 18%，依然离合理水平差得很远。AI 越容易帮你把代码写出来，知道「天花板到底在哪」、该局部修补还是该推倒重来的人，反而越值钱。

中间还有个挺有意思的小插曲：被问到四五年后 AI 从业者的出路，他很认真地先说了水电工创业，被主持人追问“机器人以后也会干水电工”之后，又改口说想做一家带点科技感的物理安保公司，还补了一句“真不是搞抽象，我真是这么想的”。挺坦诚，也挺好玩。

写在最后

13 分钟的访谈听完，留下的印象反而很朴素：数据得自己盯着看，多轮 RL 得把沙盒和 GPU 闲置捋顺，RSI 绕不开验证速度，用 AI 写代码更得先算清硬件物理上限。不管是做端侧基础模型，还是做延迟反馈与自演化 Agent，拆到底面对的其实都是同一批绕不过去的基本问题。
